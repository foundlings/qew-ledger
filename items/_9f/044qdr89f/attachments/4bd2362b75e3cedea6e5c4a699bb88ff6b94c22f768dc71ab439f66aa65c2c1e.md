# PR link declaration: design (qew 7.0.0, breaking)

Status: design, written before any code. Owner order relayed by Santa (macos-foundlings). Author: qew builder.

## 1. Problem and invariant

Today a PR's relation to ledger items is implicit: the covered `items` list is frozen at `pr open`, the `## Progress`
checklist on the forge body decides what `qew land` completes, and nothing says which items a PR finishes, only advances,
or merely touches. Result: partial-slice PRs complete whole parents, merged PRs leave items open, evidence is missing, epic
percentages are fiction.

Invariant to establish: **every PR that goes through qew carries an explicit, machine-checked link declaration held in
the ledger; merging through qew makes the ledger exactly right with no manual step.** The forge sees only a projection.

## 2. Model

A link is `(pr, item, role)`, roles:

| role | meaning at merge |
|---|---|
| `closes` | this PR completes the item (may be an epic, may be several items) |
| `remains` | partly delivered or touched; stays open; gets a comment with the PR and merge change |
| `related` | context only; shown in `qew show`, no state change |
| no-item | `--no-item REASON`: the PR relates to no item; the reason is recorded |

A PR holds exactly one of: at least one item link, or a no-item declaration. An item has at most one role per PR; a
re-role replaces it. `closes` is exclusive: at most one open PR (or one union) may `closes` an item.

Derived, never stored: a PR's `covered` set (what `pr_record.PrRecord.items` means today) is `closes + remains`. Every
current consumer of `items` (ownership rule, evidence gate, open children, `sync`) reads this derived set, so they keep
working; only `closes` is gated for delivery, `remains` is never gated.

## 3. Storage (schema 9): link events, one file each

Base requirement: no two writers touch one file. The PR mirror file (`mirrors/ITEM/TARGET-pr-N.json`) is rewritten whole
by `update_mirror`, so keeping links in it would put two agents' `pr link` into one file and one git conflict. Links are
therefore events.

- New directory `prs/_xx/TARGET-pr-N/` (sharded like `items/`, shard = last two chars of the base35 number string
  formed as for ids; the shard rule is the schema 8 rule applied to the PR key). One file per event, unique base35 time
  id, never rewritten:
  - `declared`: first file of a PR record: `{forge, url, number, opener, head, base, created}`. Present for every PR
    opened by 7.x. For a PR with an item host, the mirror file stays the forge projection (state, draft, title, blockers)
    exactly as now; `declared` adds no second copy of forge state.
  - `link`: `{item, role}`; `unlink`: `{item}`; `no_item`: `{reason}`; `member`: `{pr}` (union, section 8).
  - `merged_seen`: `{merge_sha, head_sha, source: qew|forge|offline}`; `land_pending`: `{reasons: [...]}`;
    `landed`: `{items, evidence, merge_sha}`; clears pending.
- Fold: last event per `(pr, item)` by event id wins (same rule as every other qew event, so every checkout derives the
  same answer); a concurrent `link closes` and `link remains` for one item from two clones folds to the later id and
  `qew check` reports the contested pair as a qew conflict event, not a git conflict.
- A no-item PR has no host item and no mirror file; it exists only under `prs/`. Readers that scan mirrors for
  `kind == pr` (sync, board, labels) correctly never see it: it has nothing to sync.
- One accessor module (`pr_links.py`) owns reading and folding; `pr_record.find` falls back to it when no mirror exists.

## 4. CLI

```
qew pr open ITEM [--closes A,B] [--remains C] [--related D] [--no-item REASON] --head B --what/--why/--testing ...
qew pr open --no-item REASON --head B ...        (no ITEM argument; title from --title)
qew pr link N [--closes A,B] [--remains C] [--related D] [--no-item REASON]   idempotent, add or re-role
qew pr unlink N ITEM [ITEM...]                    idempotent; unlinking the last item needs --no-item REASON
qew pr links N [--json]                           the declaration, the preflight verdict, drift
qew pr migrate [--all | N ...]                    section 9
```

- `pr open ITEM` with no role flag means `--closes ITEM` is NOT inferred: the declaration is mandatory, so the command
  refuses (exit 2) and prints the exact command with the flags filled in (`add --closes ITEM`). Rationale: an inferred
  `closes` is exactly the bug that completes whole parents. `ITEM` stays the PR's host (title, issue, claim) and must be
  named in some role or `--no-item`.
- `pr ready` and `pr merge` refuse a PR that has no declaration (a pre-7 record) with the `pr migrate` fix.
- Items are given by id, alias or `--needs`-style lists; every flag takes several; commas and spaces both split.
- All of them are `QEW_OFFLINE`-safe: the ledger write happens first, the forge projection is best-effort and retried by
  `qew sync`; a forge failure never loses the declaration.

## 5. Forge projection

A single machine-owned block in the PR body:

```
<!-- qew:links v1 -->
Closes: ID title, ...
Remains: ...
Related: ...
No item: reason
<!-- /qew:links -->
```

- Regenerated on every link change and by `qew sync`; never contains GitHub closing keywords (`pr_body.refuse_closing_references`
  already enforces this on every body qew writes, the block is covered by the same test).
- qew never reads the block back as input. `qew check`, `pr links`, `pr ready` and `pr merge --check` compare it with the
  projection and **warn** on drift (edited by hand, stale after an offline link); `pr sync` rewrites it.
- The `## Progress` checklist, `pr check`, `--allow-unticked`, `pr_unticked` and `pr_checklist` are **removed** in 7.0.0
  (the declaration supersedes them; the ticked/unticked data migrates, section 9). `pr check` becomes a one-line error
  naming `pr link`. Dead code is not kept as a compatibility path.

## 6. Preflight (ledger only, fast, before the project gate)

`qew pr merge N --check` becomes the preflight and gains `--ledger-only`: it reads the ledger snapshot, never the forge,
never a hook, writes nothing. A harness that runs a 50 minute gate calls it first. `pr ready` and `pr merge` run the same
function. For each `closes` item it checks, collecting EVERY refusal (not the first), each with the fix command:

1. the item exists and is not already completed/closed (completed by another PR: name it);
2. it is claimed by the merger, or `--other-author/--integrator` is in force (existing ownership rule);
3. every `needs` is completed, or is also `closes` of this PR / its union;
4. children: every child is completed, or is `closes` of this PR; an `closes EPIC` only when every descendant will be
   complete after this PR; any other open child makes the PR a partial slice, so the fix text is
   `qew pr link N --remains EPIC` (the partial-slice protection);
5. evidence can be satisfied: the item already has evidence on the head, or the head range holds at least one change id
   (jj change id on the target after merge) that auto-land will record. A PR whose head has no change id of its own, or whose
   vcs is not recognised, fails here, not after the gate;
6. no other open PR `closes` the same item (conflict names the PR and both fixes), and no declared `closes` in a member
   of the same union disagrees with a `remains` in another (section 8);
7. no `closes` item is a draft (existing hold).

`remains` and `related` items must exist (typo guard) and may be in any state; a `remains` item that is already completed
is a warning (stale declaration), not a refusal.

Cost: one snapshot (already loaded by `load`) plus an index of children and of open PR links, both O(items + links); the
epic walk is O(descendants of the epic). Measured against the existing `merge --check` it adds no forge call.

## 7. Merge and auto-land

`qew pr merge N` order: ownership/draft/mergeable/checks (forge refusals, unchanged) -> preflight re-run -> **the caller's
gate is outside qew and already finished** -> re-validate cheaply on a fresh snapshot -> forge merge at the checked head
-> auto-land.

- **Never fail after the gate for bookkeeping.** Between preflight and merge an item may have moved (completed by someone
  else, claim changed, a new child). Re-validation classifies each `closes` item: *satisfied* (already completed by this
  PR or an equivalent state), *flagged* (cannot be completed now). The merge proceeds either way; only a moved PR head
  (the forge's checked-head merge refusal) rejects it. Flagged items go to a `land_pending` event with the exact
  reason; the merge output prints them and the repair command.
- **Auto-land** (replaces the separate `qew land` step, which stays as the repair command and the offline path):
  1. read the merge commit from the forge (or, offline, section 11);
  2. for every `closes` item (children before epics): record evidence = the PR's own change ids (range base..head) plus the
     merge commit when the vcs gives it a change id, then `complete` it;
  3. epics whose children are now all completed complete (existing "an epic finishes with its last child" rule, now also
     run for epics outside the declaration);
  4. `remains`: comment `pr #N merged (<merge>): partial delivery`; `related`: comment only;
  5. `merged_seen` and `landed` events; clear any `land_pending`.
- `qew land N` = re-run steps 2-5 for a merged PR (idempotent), clearing `land_pending`; `qew repair` lists every merged
  PR whose declaration is not landed and runs it for all.
- Merges that no qew command ran (UI, auto-merge, queue) are still caught by the existing post-shell hook and `qew sync`:
  they record `merged_seen` and run the same land, since the declaration is in the ledger and needs no forge text.

## 8. Locking

Today `replication.section` wraps writes; the forge call is outside it. The new rule, enforced by a test that fails if the
write lock is held across a forge call or the gate:

1. take a snapshot with its version token (hash of the folded heads of the items and the PR link set involved);
2. validate and call the forge without the lock;
3. take the write lock for the short final commit; re-read the token; if it changed, re-validate (cheap, ledger-only) and
   write, classifying differences as satisfied/flagged per section 7; never loop forever (one retry, then `land_pending`).

## 9. Unions

`qew pr union N M ...` pushes the lead's branch as today and records `member` events on the lead. The lead's effective
links are the **union of its members' links, computed at read time** (not copied), so `pr unlink` on a member still
propagates, and jj change ids of members stay ancestors (merge commits only, never a squash: unchanged code path).
Conflicts caught in preflight: an item `closes` in one member and `remains` in another (the item has other open work: refuse,
fix: re-role one); an item `closes` in two members is fine (one landing). The union's projection block lists each
member's three lists under its PR number. A member merged through the lead is marked `merged_seen` with `via: lead`.

## 10. Migration, versions, mixed-version safety

- **Schema 9** (`prs/` directory + link events) declared in `qew-ledger.toml`; this qew reads 1-9. An older qew already
  refuses an unknown `schema_version` (`ledger_config` strict check), so it cannot silently write a ledger it does not
  understand; `qew migrate-layout` declares 9 (a no-move step: it only writes the version and a `prs/` marker commit).
- Repo floor: `.qew/config.toml [qew] minimum_version = 7.0.0` with `src/qew/__init__.py`; Foundlings raises its own.
- `qew pr migrate`: for each open or merged PR record without a declaration, one ledger-side pass: ticked Progress boxes
  (read from the forge body, or the mirror's recorded `items` when the forge is unreachable) become `closes`, unticked become
  `remains`, `dropped` entries become `related`, a PR with no boxes and no items becomes `no_item "migrated"`. A merged PR
  whose items are not completed gets `land_pending` so `qew repair` finishes it. One commit, idempotent, `--dry-run` prints
  the declaration per PR. Old PR bodies keep their Progress boxes (cosmetic) until `pr sync` rewrites the body with the block.
- Concurrency between agents on different versions: a 6.x qew is refused by the schema check as soon as the ledger is on 9;
  the forge-side body is the only shared surface and 6.x edits to it are ignored by 7.x (block rule, section 5).

## 11. Offline and forge-less

The ledger is the source of truth, so none of this needs a forge: `declared`/`link` events are written with `QEW_OFFLINE=1`.
For a ledger with no forge target at all, `qew pr open --local --head BOOKMARK ...` writes a `declared` event with a
`local-<id>` key instead of a forge number, and `qew pr land LOCAL --change CHANGE` records that the head change reached
the target (ancestry check with `code_vcs.is_ancestor`) and runs the same auto-land. Offline merge detection for forge PRs:
`qew sync`/`qew repair` mark `merged_seen` when the PR head is an ancestor of the target branch in the local checkout even
if the forge cannot be read.

## 12. `qew check` audit

New structural findings (errors unless noted):
- a merged PR with a `closes` item that is not completed and has no `land_pending` (unlanded);
- a merged PR with no declaration and not migrated (unlinked);
- an open PR declaring `closes` on an item another open PR also `closes` (conflict);
- a link naming a missing item; a `link` for two roles from different clones (contested; a conflict event);
- body drift (warning).
`qew status` and `qew prime` surface the count of `land_pending`.

## 13. Drawbacks and how each is handled

| drawback | handling |
|---|---|
| schema change and migration | additive directory; one idempotent `pr migrate`; floor via schema check |
| old qew writes a PR the new one cannot read | refused by the strict schema check before any write |
| forge body drift | block is write-only for qew; warn, never trust |
| item closed by several PRs | `closes` exclusive across open PRs; sequential partial slices use `remains` then a final `closes` |
| unions | derived aggregate, conflicts in preflight, no squash |
| epic auto-complete race | completion is idempotent and evented; the second writer sees `already completed` |
| offline merge | ancestry detection and `merged_seen` from the local checkout |
| preflight cost on large epics | O(descendants) over the loaded snapshot, no forge |
| declaration burden on agents | the refusal prints the exact command; `pr open` flags are one line |
| removing the checklist breaks habits | `pr check` errors with the replacement; documented in the release notes and Foundlings rules text |
| lock contention | write lock only for the final short commit; test forbids lock across forge or gate |
| merge succeeds but bookkeeping drifts | `land_pending` + `qew repair` + `qew check` audit make it visible, never silent |

## 14. Work breakdown (ledger children of the epic)

1. Schema 9 + `prs/` event store, fold, `pr_links.py`, `pr_record` fallback, `migrate-layout` to 9.
2. `pr open` declaration, `pr link/unlink/links`, no-item PRs.
3. Projection block, drift warnings, removal of the Progress checklist and `pr check` / `--allow-unticked`.
4. Ledger-only preflight (`--ledger-only`), partial-slice protection, cross-PR conflict, `pr ready` hook-up.
5. Merge re-validation, auto-land, `land_pending`, `qew land`/`repair`, short-lock two-phase.
6. Union aggregation.
7. `pr migrate`, `qew check` audit, offline/local PRs.
8. Specs, README, guide text for Foundlings, release 7.0.0 with `minimum_version = 7.0.0`.

Each step is red-first at command level (golden walk plus refusal walks); the new gates (lock-not-held-across-forge, no
closing keywords in the block, preflight collects all refusals) ship with tests that fail on the bad shape and pass on the
good one.
